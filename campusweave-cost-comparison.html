Architecture and cost model

Build for ten years. Upgrade by design.

A long-term technology decision and transparent monthly comparison for the CampusWeave PWA, system of record, documents, notifications, email and context-aware AI.

Preferred production foundation

React PWA + Java/Spring modular monolith + managed PostgreSQL, packaged portably and initially operated on AWS managed services.

⚠
Ten years does not mean freezing the 2026 stack. It means controlled upgrades, tested recovery, backward-compatible releases and replaceable providers. Cloud cost is still not total product cost.

Software architecture decision

Portable core over the cheapest runtime

CampusWeave is a transactional, audit-heavy, multi-tenant ERP. The database model and API contracts must outlive any single UI framework or cloud vendor.

PreferredReact PWA + Java 25 LTS + Spring Boot + PostgreSQL

Deploy the API as an OCI container on ECS Fargate, use RDS PostgreSQL Multi-AZ for the system of record, S3-compatible storage for documents, an OIDC identity adapter and a transactional outbox with SQS. The current Vinext beta remains prototype-only.

Strong reason

  • The relational school-domain model—not the web framework—is the durable product asset.
  • Frontend, identity, storage, AI and cloud providers can change without rewriting admissions or family history.
  • Managed PostgreSQL and queues protect transactions and scheduled work while containers preserve a provider exit.

Reliability price

AWS Multi-AZ, load balancing, logs and disaster recovery will cost more initially than the calculator's launch stacks. That premium buys recoverability and operational control; it must be priced after availability, recovery and retention objectives are approved.

Included capability scope

Notifications and documents are costed

These are infrastructure allowances and workload assumptions. Product implementation, permissions and delivery testing still belong in the MVP build.

Parents and schools · notifications

  • In-app inbox and standards-based Web Push for desktop and mobile browsers.
  • Transactional email through SES.
  • Scheduled and retry-safe delivery through the outbox and SQS, with dead-letter handling.
  • WhatsApp and SMS volumes are modelled; contracted per-message rates remain calculator inputs.

Private documents · upload and download

  • S3-compatible private object storage with application-owned metadata.
  • Upload writes, authorized download reads, stored GB and delivered GB are included in each workload.
  • Downloads require API authorization and time-limited access; public bucket access is excluded.
  • Virus scanning, document extraction and long-term archival need separate measured allowances when enabled.

Operating discipline

Cost controls before complexity

Controls to implement from day one

  • One multi-tenant production database, not one project per school.
  • Provider spend caps, upload quotas and per-school AI budgets.
  • In-app inbox and Web Push first; paid messaging only for consented, high-value events.
  • Portable document references and a tested R2 migration path.
  • Monthly unit metrics: cost per active school, student, document GB, delivered notification and AI task.
₹50,000/mo

At the scale workload, every ₹0.10 per WhatsApp message adds ₹50,000. Messaging procurement can therefore outweigh the complete Cloudflare application runtime.
