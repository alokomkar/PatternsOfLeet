Performance implications of Kotlin + Spring Boot vs. pure TypeScript

CampusWeave's actual workload is I/O-bound CRUD — database reads/writes and calls to MSG91, Razorpay, Google Maps, Gemini and WhatsApp — not CPU-bound computation. For that profile the practical difference between the two stacks is small, and where a difference exists it doesn't uniformly favor TypeScript.

DimensionKotlin + Spring Boot (GraalVM native, Cloud Run)Pure TypeScript (Node, Cloud Run)Verdict
Cold startSub-100–500ms with native compilation — the reason this stack was chosenAlso fast on Cloud Run, typically 100–300msComparable — the GraalVM choice specifically closed this gap
Warm request latency, I/O-bound workFast — this is what JVM concurrency is built forFast — this is what Node's event loop is built forNo meaningful difference for CRUD/API-call-heavy work like this app
Using multiple vCPUs in one containerReal advantage — JVM threads (and Java 21+ virtual threads) use all cores natively in one processSingle-threaded per process; using >1 vCPU well needs clustering/worker processesKotlin edge — a 2-vCPU Cloud Run instance is simpler to actually use fully with Spring
Memory footprintNative image is lean — comparable to Node, nowhere near a traditional JVM's overheadNaturally leanComparable — native compilation mostly erases Node's traditional advantage here
Consistent performance from request 1Yes — AOT-compiled, no JIT warm-up curveYes — V8's warm-up is much less pronounced than a traditional JVM's anywayComparable, both fine
Build / deploy timeNative image compilation takes minutes in CI, not secondsBuild/bundle is fastTypeScript edge — a developer-velocity cost, not a runtime one
Library compatibilityOccasional friction: reflection-heavy libraries need extra GraalVM config to compile nativelyNo such constraintTypeScript edge, but narrow — mainstream Spring libraries are officially native-supported in Spring Boot 4
The one thing worth internalizing: this isn't "JVM is slow, avoid it" — that reputation predates GraalVM native images and virtual threads. The actual trade made here was Kotlin's build-time tax (slower CI) in exchange for using the team's own language and getting genuinely better multi-core utilization per container — not a runtime performance sacrifice.
Where it would matter differently: if CampusWeave later adds something genuinely CPU-bound in-process — computing search-ranking scores over large result sets, or heavy in-app document processing instead of delegating to Gemini — Kotlin's true parallelism becomes a bigger, not smaller, advantage over Node's single-threaded model. Nothing in the current flows needs that yet, but it's a reason this choice ages well rather than needing revisiting.
