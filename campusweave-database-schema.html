READING THE DIAGRAM

Badges and notation

PKPrimary key — uniquely identifies a row
FKForeign key — references another table's PK
1 · NOne row on the left relates to many on the right
1 · 1Exactly one row on each side (e.g. one application → one admission)

Only the sixteen relationships that define the schema's shape are drawn as lines. The rest of the foreign keys — school_id chains, staff ownership, academic-year scoping — are visible as FK badges on each table without cluttering the diagram with every possible connector.

DESIGN PRINCIPLES

Why the schema is shaped this way

Tenant scope on every row that needs itEvery table that isn't platform-global carries school_id or campus_id, enforced by Supabase Row-Level Security — not just application-layer filtering.
The outbox, not a message bus, is the async boundaryoutbox_events commits in the same transaction as the domain write it originates from. No table has a hard FK into it — every domain writes to it, which is exactly why the diagram treats it as a soft reference, not a drawn line.
Source and verification are first-class, not implicitschool_attributes and document/admission records carry source and verification timestamps directly — matching the platform-verified vs. school-submitted vs. parent-review distinction established in SCHOOL_PLATFORM_BLUEPRINT.md.
Payments are polymorphic on purposepayments.payable_type/payable_id can point at an admission, an order, or a fee plan — one ledger table for every payable thing, instead of duplicating payment-state handling per domain.
