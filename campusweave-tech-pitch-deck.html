CampusWeave

How the platform is built, why each piece was chosen over its alternatives, and what it costs to run at every stage from pre-pilot to 300 schools.

Why this stack

Four decisions, one thesis: don't spend runway on infrastructure the business hasn't earned yet.

1 · Capital efficientRuns on $45–140/month through Pilot and Growth, versus $390–1,800 on an AWS/Java default. That's runway, not a rounding error.
2 · Built for India, not adapted to itUPI-first payments, WhatsApp-first messaging, DLT-compliant OTP delivery, India-priced compute — chosen for the actual customer, not a generic global default.
3 · No single point of lock-inEvery external dependency — identity, payments, maps, AI — sits behind a swappable adapter. Any one provider can change without touching domain logic.
4 · Nothing beta in the critical pathEvery core platform here — Cloudflare, Supabase, PostgreSQL, Spring Boot — runs production workloads at massive scale for other companies today.

Data model & analytics

Every table exists because a flow needs it. Every AI output exists because a person reviews it.

Not a claim — a discipline we ran against the system itself before putting it in this deck.

36 tables, tenant-isolatedEvery row that isn't platform-global carries school_id/campus_id, enforced by Postgres Row-Level Security — not just application-layer filtering. 300 schools' data can't leak into each other by construction, not by discipline.
Traced, not assumedEvery table was checked against an actual flow's stage or sequence diagram; every analytics claim traced to the specific field it reads. That process found and fixed ten real gaps — including order_items having no price, which meant revenue itself wasn't computable.
One dashboard per roleParent, centre head, counsellor, school admin, teacher, finance, vendor, platform engineering each see metrics scoped to what they're allowed to know — the same tenant boundary as the schema underneath.
AI proposes, a person decidesEvery AI-generated insight is written as a reviewed proposal, never an automated action. If the model can't name a specific, actionable cause, it doesn't generate the insight.

Full schema and analytics architecture: campusweave-database-schema.html and campusweave-analytics-architecture.html.

Flow 1 of 5 · Parent-facing

A parent finds the right school in under five taps.

Search location + filters→ Geocode address→ 5km radius + facet query→ Ranked, comparable results
React PWA Kotlin + Spring Boot Supabase Postgres + PostGIS Google Maps
Why: PostGIS answers "within 5km" directly inside the database — no separate search service to run, scale or pay for. Google Maps for geocoding: the trusted, well-documented default that parents' own devices already resolve addresses against.

Flow 2 of 5 · Platform-facing

Thousands of school profiles, without thousands of hours of manual entry.

Crawl public sources→ Store raw snapshot→ AI extracts structured fields→ Confidence-gated human review→ Verified record
Kotlin + Spring Boot Cloudflare R2 Gemini API Supabase Postgres
Why: AI does the first pass at a scale no team could hand-enter. A person still verifies before anything is shown as "platform-verified" — data trust is the actual product here, not just the listing count.

Flow 3 of 5 · Revenue-adjacent

Every step that touches a seat or a rupee is transactional, not best-effort.

OTP verify→ Book appointment→ Counsellor follow-up→ Application→ Payment→ Admission gate→ Notify
Supabase Auth MSG91 Kotlin + Spring Boot Supabase Postgres Cloudflare R2 Razorpay Postgres outbox + scheduler WhatsApp
Why: UPI-first because that's how these parents actually pay — zero transaction fee on the dominant rail is a bonus, not the reason. Seat allocation runs inside a real database transaction, so two families can never be admitted into the same last seat.

Flow 4 of 5 · School-facing

One codebase, one database, six domains — until the business proves it needs more.

Directory & Family Discovery & Search Admissions Academics Commerce & Billing Communications / Documents / AI
Kotlin + Spring Boot (single deployable) Supabase Postgres (single governed database)
Why: Microservices solve a staffing and scaling problem this stage doesn't have yet. A modular monolith keeps domain boundaries clean enough to split out later, without paying distributed-systems tax today.

Flow 5 of 5 · Retention-adjacent

The channel is chosen by where parents actually read, not by what's easiest to build.

Domain event commits→ Outbox row→ Worker claims it→ Queue retries→ Channel policy decides
Postgres outbox + scheduler WhatsApp Business API Web Push Resend (email) MSG91 (SMS fallback)
Why: WhatsApp is primary, not a fallback behind email — matches how this parent segment actually engages. A decision made for this market specifically, not inherited from a generic template.

No rewrite risk if we ever do move: the application is Kotlin on Spring Boot, running today as a GraalVM-native container on Google Cloud Run — chosen specifically so it scales to zero like an edge function instead of carrying a traditional multi-second JVM boot. If a school contract requires SOC2/ISO27001 certification or true multi-region failover, the exact same container image redeploys to AWS Fargate. Same codebase, same framework, different hosting — that day is a deploy, not a rewrite.

The obvious fast option

Firebase is fast to start and expensive to grow out of.

DimensionSupabase (our choice)Firebase
Relational fitStrong — real PostgreSQL, PostGIS, pgvectorWeak–medium — document model fights relational reporting
Cost predictabilityGood — base plan plus compute add-onsWorkload-sensitive — bills per read/write/delete/index
Exit exposureModerate — database stays portable SQLHigh — a later migration means re-modeling the data, not moving it
Why it matters: our core asset — admissions, payments, seat allocation, funnel/attribution analytics — is exactly the transactional, audit-heavy, relational workload Firestore is weakest at. It's genuinely cheaper at Pre-pilot (~$0–2/month); the curve inverts by Growth as query complexity rises with no matching drop in per-operation billing.

We're not locked in — we're sequenced

This isn't the forever stack. It's the right stack for the stage we're at, with the next stage already written down.

  • Move the same containerized Kotlin/Spring Boot application to AWS Fargate at Growth-tier scale (50+ schools) — the point real operational blast radius justifies the operational cost. No rewrite, ever — the container moves, only the hosting does
  • Or the moment any single school contract requires SOC2/ISO27001 certification or true multi-region failover — whichever comes first
Every provider in this deck — identity, payments, maps, messaging, AI, even the database — sits behind a replaceable adapter for exactly this reason.
